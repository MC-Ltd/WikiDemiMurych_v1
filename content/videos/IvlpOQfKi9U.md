Очевидно, что если у Вас уже согласно спецификации должен быть обьект, обслуживающий String, то нет никакого смысла придумывать другой для того же самого.
> 
> Тут Вы сделали очень верную ремарку про то чей это обьект.
> Мне нужно всегда уточнять, где речь идет про обьект как тип JavaScript и обьект как структура данных на уровне RunTime. 
> 
> При этом, почти всегда любые данные на уровне JS это обьект на уровне RunTime. И только в случае оптимизаций со стороны RunTime может оказаться немного иначе.
> 
> 
> Штука в чем. Спецификация JS имеет ряд типов, которые по умолчанию возвращают Primitive Value. При этом, спецификация, определяет алгоритм как это делается. При этом спецификация определяет детально, что значат  те или иные части (команды) алгоритма. 
> Связывания данных с идентификатором в рамках спецификации, это оперцация let/set ( не путать с let/set из JS). При этом, в рамках спецификации, в главе 5.2 описано как работают let и set. Где прямо сказано, что это такая операция, которая является эквивалентом Reference (ссылочному) типу данных. Который никак не может быть ничем иным кроме обьекта.
> 
> В итоге и происходит - когда я привык называть все обьектом, потому, что по сути так оно и есть. И иначе оно не может быть организовано за исключением специфических случаев. 
> 
> Кроме этого, как я рассказывал в одном из видео, Брендан Эйк (ключевой разработчки архитектуры JS) заявлял, что появление типов, которые по умолчанию возвращают Primitive Value, хотя при этом должны вести себя как обьекты - это было компромиссное решение, которое было навязано менеджментом того времени. И с самого начала ничего подобного не планировалось, но все должно было быть одним чистым типом Object.

> @leilaoskanova7557 var bar = () => { 
>     console.log(foo); const foo = 42;
> };
> console.log('<< 1 >>'); bar(); console.log('<< 2 >>'); //  Этот код упадёт именно по причине ThrowReferenceErrorIfHole. Если просто - в результате компиляции в байткод интерпретатор не сможет закинуть undefined в аккумулятор, так как const не определена как undefined. В аккумулятор забросит "Hole". И рухнет при попытке выполнить выражение "foo" из строки console.log(foo). При этом, первый прогон (синтаксиса) не упадёт. Чтобы поддержать такое поведение потребовалось вкорячить инструкции: LdaTheHole ( вместо lda value ), и ThrowReferenceErrorIfHole, которой нет совсем при использовании var ( так как не нужно обеспечивать проверку ).

примеры из видео понятны, то немного странны
например код
```
var theFoo = 1;
function doIncrement() {
     theFoo++;
     return theFoo;
}
```
позволяет написать функция которая будет прибавлять к глобальной перменной 1 при каждом вызове,
и сложно представить как это можно оптимизировать на вид, где переменная была бы определена внутри фукнции.

поэтому при сравнении такого кода (как выше) и кода
```
function doIncrement() {
    var theFoo = 1;
     theFoo++;
     return theFoo;
}
```
приводит только к мыслям - "ага, определять перменные вне фукнции и использовать их в функции - это плохой для перфоманса подход, потому что создаются лишние обекты в памяти. как это применить? - хрен его знает"
