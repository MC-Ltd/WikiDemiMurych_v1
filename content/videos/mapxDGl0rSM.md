4:59:47 В JS нет возможности перехватить исключение произошедшее в другом (асинхронном) стеке вызова, только если сама функция специально не "перенаправляет" `throw` в `Promise#catch` (явно или неявно через `async function`).
Поэтому, сама задача не имеет смысла, т.к. покрыть "все возможные ситуации" всё равно невозможно.

А пример с Promise executor мне вообще не понятен. Это тоже самое, что и:
```
const { promise: deferred, resolve, reject } = Promise.withResolvers();
const executor = ( fn) => {
  try { resolve( fn() );  }
  catch( e ) { reject( e ); }
};

executor(() => { setTimeout(() => { throw 'Unhandled error' }) });

deferred.then(() => {
  console.info('Reached code');
}, (err) => {
  // Этот обработчик НЕ вызовется
  console.warn('Unreached code. error =', err);
})
```
Т.е., всё равно тот же самый (синхронный) `try / catch` используется при вызове Promise executor.

Одним из возможных решений, было бы подписываться на `window#error` в браузере, `process#unhandledRejection, process#uncaughtException` в ноде и на аналогичные события в других рантаймах (агентах). Однако, это решение костыль, т.к. мы вмешиваемся в логику ВСЕХ необработанных ошибок, а не только тех, которые будут в переданной нам функции. А это может привести (и обязательно приведёт) к коллизиям.

> **[@AsForJS](https://www.youtube.com/channel/UC8aUxVCtAmBtKXmYdPmzjeA)** *[18.12.2023 06:02](https://www.youtube.com/watch?v=mapxDGl0rSM&lc=UgwFWPZje1S6djWEuE94AaABAg.9y8dewLAi3N9ySSgilHGh2)*

> В JS нет другого асинхронного стека вызова.
> В JS нет стека вызова вообще.
> В JS есть Execution Context Stack, который отчасти напоминает стек вызова, но им не является.
> В JS Execution Context Stack существует в единсвенном экземпляре и строго гвозями прибит к Agent-у.
> 
> В рамках Agent-а может выполняться только один Job, описание которого делается через Execution Context Stack.
> 
> 
> await не перенаправляет никакие throw никуда.
> await все что делает  - это проверяет состояние промиса, и если он Rejected то генерирует throw с данными из Rejected промиса. Что не может быть никаким эквивалентом throw.
> 
> Потому, как программист может вызвать именно throw в качестве фиксации особой ситуации, а может разрешить промис используя Reject функцию из Executor-а.
> 
> Без вмешательства прогрормамиста, throw в окружении Promise приведет его в Rejected состояние. 
> 
> После чего это состояние и определяет await.
> 
> Аналогично, если программист просто сделает Reject своего промиса, без вызова throw - то есть без обозначения особой исключительной ситуации, то await ровно точно так же привет к генерации throw для async функции.
> 
> Задача имеет очень большой смысл в аспекте, когда Вы имеете чужой сторонний код и не знаете каким образом этот код функционирует. 
> 
> Вы не проконтролируете работу этого кода  при помощи try catch.
> Но проконтролируете почти все заверну исполнение этого кода внутрь Promise.
> 
> Исключением является особенности реализации внешнего API такого например как setTimeout. Котороый в рамках браузера, или стандарта HTML5, выписан как задача которая ставится в Execution Context отдельным Job.
> 
> Но и это можно уже контролировать используя Shadow REALM.
> 
> Хотя, конечно последнее в стадии утверждения.
